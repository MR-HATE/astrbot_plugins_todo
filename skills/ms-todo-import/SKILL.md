# Microsoft To Do 待办导入

把「一句话计划」变成用户手机上真实可见的待办清单。核心是**先对齐、再写入**——写错了
会污染用户的真实任务列表，而 To Do 没有服务端回滚。

## 何时使用

**用**：
- 用户描述接下来要做的事、给出计划、一次说出多件事；要求把某件事记进待办；
- 用户**询问待办情况**（"今天还有什么要做的""上周的事做完没""XX 列表里还有啥"）
  → 调用 `ms_todo_list_tasks` 读取真实状态，不要凭空回答。

**不用**：纯闲聊、提问、查资料；用户只是在感叹（"最近好忙啊"）而没有具体要做的事。
后者应当追问一句"要不要我帮你理成待办清单"，而不是直接调用工具。
只有当用户明确给出"要做什么"、或明确询问待办情况时才动手。

> 能力边界：目前支持**导入**、**查看列表**、**读取待办与完成状态**、**修改/完成/删除待办**、
> **给待办追加子步骤**。还不能改列表名、不能移动任务到别的列表、不支持重复任务——
> 用户要这些时如实说明。

## 改动已有待办

| 用户想做什么 | 工具 |
| --- | --- |
| 改期、改优先级、改标题、改备注、清除截止时间 | `ms_todo_update_task` |
| 标记完成 / 取消完成 | `ms_todo_complete_task`（`completed=false` 是取消） |
| 追加子步骤 | `ms_todo_add_checklist_items` |
| 删除一条任务 | `ms_todo_delete_task`（**两阶段确认**） |
| 删除整个列表（连同里面的任务） | `ms_todo_delete_list`（**两阶段确认**） |

**定位方式**：用 `query`（标题关键词，模糊匹配）或 `task_id`。二者的选择：

- 用户只说了一个名字 → `query` 就够了；
- 工具返回了候选清单（匹配到多条）→ **把候选给用户看，让他选**，然后带上他选的
  `task_id`（或更精确的标题）重新调用。**绝对不要自己挑一个改**。

**删除必须两阶段**：

1. 第一次调用时 `confirmed` 留空 → 只返回"将删除什么"，把这段**原样发给用户**并等确认；
   - 删任务：`ms_todo_delete_task(query=...)`
   - 删列表：`ms_todo_delete_list(list_name=...)`，它会顺便告诉用户列表里有多少任务
     （含几条未完成）——这些信息要转达；
2. 用户确认后才 `confirmed=true` 再调用一次。用户反悔就不要调用，删除不可恢复。

**删列表 vs 删任务**：用户说"把上海出差那个列表删了"用 `ms_todo_delete_list`；
说"删掉买菜这条"用 `ms_todo_delete_task`。拿不准时先问一句——删列表会连带删掉里面所有任务。
Microsoft To Do 的**默认列表不能删除**（工具会拒绝并说明）。

**改期**支持相对说法（"周五"）和绝对日期（"2026-09-18"）；只给时刻（"改到下午三点"）
会保留原来的日期。用户说"不用设截止时间了"用 `clear_due=true`。

## 读取待办与完成情况

`ms_todo_list_tasks(scope=..., list_name=..., limit=...)` —— **只读**，不做任何修改。

| scope | 含义 | 适用问法 |
| --- | --- | --- |
| `pending`（默认） | 未完成且今天到期或已逾期 | "今天还有什么要做的" |
| `today` | 仅今天到期 | "今天到期的有哪些" |
| `overdue` | 已逾期且未完成 | "有什么逾期了" |
| `upcoming` | 未来 7 天内到期 | "接下来几天要忙什么" |
| `completed` | 已完成 | "这周完成了哪些""上周的事做完没" |
| `all` | 全部 | "把 XX 列表给我看看" |

`list_name` 留空 = 汇总用户所有列表（结果里会标注每条属于哪个列表）。

结果里的状态标记：

- `⬜` 未完成 · `🔄` 进行中 · `✅` 已完成 · `⏳` 等待他人 · `💤` 已推迟

**回答时要用这些真实状态**，不要臆测。如果用户问"做完没"而结果里只有未完成的项，
说明该项确实还没完成；如果某项不在结果里，可能是它的截止日期不在该范围内，
这时可以换 `all` 或指定列表再查一次，而不是直接说"没有这件事"。

## 工作流程

1. **判断与追问**：能从原话确定要做的事就直接进行；如果某件事含糊到无法写成一个动作
   （"处理一下那个事"），先问清楚，不要臆造。
2. **整理成任务数组**：按下面的「抽取规则」拆分，换算时间，判断优先级。
3. **调用 `ms_todo_import_tasks`**：带上 `tasks` 和 `plan_name`，**`confirmed` 必须留空**。
4. **把返回的预览原样发给用户**，并询问确认。不要自己改写预览内容，也不要替用户决定。
5. **用户确认后**调用 `ms_todo_confirm_import`（`action="confirm"`）；
   用户反悔则用 `action="cancel"`。写入成功后把结果回执发给用户。

> 如果用户一开始就明确说"不用确认，直接导入"，且配置允许，才可以用
> `confirmed=true` 一步完成。默认一律走"预览 → 确认"。

## 抽取规则

- **一件事 = 一个 task**。判断标准：能独立完成、独立打勾。
  - 「订酒店」和「订机票」是两件独立的事 → 两个 task。
  - 「搬家」下面有「找搬家公司 / 打包 / 转移宽带」→ **一个 task + 三个 steps**。
- **不要过度拆分**：把「给客户回邮件」拆成「打开邮箱 / 写邮件 / 发送」是错的，那是一个 task。
- **steps 只放真正的子步骤**，每条是一句话，不要超过 5 条。
- **title 写成动作短语**，一眼能看懂要做什么；不要把时间塞进标题（时间放 `due_date`）。
  - 好：`订好上海的酒店`
  - 差：`周三之前要把酒店订了（重要）`
- **note 放补充信息**：地点、金额、联系人、单号。没有就留空。
- **importance**：用户说"重要/紧急/别忘了"→ `high`；说"不急/有空再说"→ `low`；
  其余 `normal`。不要所有任务都标 high。

## 时间处理

把用户说的相对时间**换算成绝对日期**后再填（今天是几号见系统提示；工具也会用配置时区兜底解析）。

| 用户说法 | 填什么 |
| --- | --- |
| 「周三前」「这周五」 | `due_date` = 最近的那个周几 |
| 「下周三」 | `due_date` = 下一个自然周的周三 |
| 「明天下午三点」 | `due_date` + `due_time` = `15:00` |
| 「月底」「下个月」 | ⚠️ 无法确定具体日期时**不要猜**，留空并在回复里说明 |
| 「每天」「每周五」 | 重复**只作用在提醒上**：填 `remind_repeat`（见下） |

**三条硬规则**：

1. **没有时间信息就不填 `due_date`**，不要默认成今天或明天。
2. `due_date` 只用 `YYYY-MM-DD`；`due_time` 只用 24 小时制 `HH:MM`。
3. `remind_at` **只在用户明确要求提醒时才填**，格式 `YYYY-MM-DDTHH:MM`。
   To Do 自身的提醒 + AstrBot 的定时任务都会用到它。

## 提醒与重复

`remind_at` 到点时，除了 To Do 自己的通知，**机器人也会在原会话里主动提醒一次**
（插件会调用 AstrBot 内置的定时任务）。

| 用户说 | 怎么填 |
| --- | --- |
| 「出发前一天晚上 8 点提醒我」 | `remind_at` = 那天的 `20:00` |
| 「每天早上 8 点提醒我」 | `remind_at` = **明天** `08:00`，`remind_repeat` = `daily` |
| 「每周五下午 3 点提醒我」 | `remind_at` = **最近的周五** `15:00`，`remind_repeat` = `weekly` |
| 「每月 10 号提醒我交房租」 | `remind_at` = **最近的那个 10 号** `09:00`，`remind_repeat` = `monthly` |

⚠️ **`remind_repeat` 的星期/日期是从 `remind_at` 推导的**，所以 Weekly/Monthly 时
`remind_at` **必须落在用户说的那个星期几/日期上**。用户说「每周五」，你却把
`remind_at` 填成周三，提醒就会在每周三响。不确定就先问一句。

另外：

- 重复只覆盖**提醒**，任务本身不会自动重建；
- 任务被标记完成后，它的提醒会被**自动取消**；
- 平台不支持机器人主动发消息时（如 QQ 官方接口），提醒不会创建——结果里会说明，
  这种情况要如实转达用户，别让他以为到点会收到消息。

更多时间写法与边界见 `references/time-expressions.md`。

## 目标列表

按这个优先级决定 `plan_name` / `list_name`：

1. 用户点名了列表 → 用 `list_name`（例："记到工作列表"）。
2. 用户给这次计划起了名字（"下个月搬家"）→ `plan_name` 用「搬家」这种短名词。
3. 都没有 → 用 `plan_name` 概括本次内容（如「本周安排」），别用「待办」「任务」这种无信息量的词。

列表不存在时插件会自动创建；用户如果想记进已有列表又拿不准名字，
可以先调用 `ms_todo_list_task_lists` 看看有哪些列表。

## 输出模板

预览由工具返回，**原样转发**即可。若需要自己补充说明，只在末尾加一句。

写入成功后的回复示例：

```
已经把 3 件事加进「上海出差」列表：
1. 订好酒店和机票 —— 9/16（周三）
2. 收拾行李 —— 9/15（周二），晚上 8 点提醒你
3. 提前值机 —— 9/15（周二）
打开 Microsoft To Do 就能看到。
```

## 异常与降级

| 情况 | 怎么回 |
| --- | --- |
| 提示未绑定账号 | 引导用户发送 `/todo login`，并说明"在手机上打开链接输码即可，不用在服务器操作" |
| 提示授权失效 | 让用户重新 `/todo login`，不要反复重试同一个工具 |
| 预览里有「⚠️ 需要留意」 | **必须转达给用户**，这些是日期没解析出来、提醒已过期之类的真实问题 |
| 解析不出待办 | 换一种问法让用户说清楚要做的事，不要自己编内容 |
| 提示列表相关错误 | 用 `ms_todo_list_task_lists` 查一遍现有列表再重试 |
| 提醒接口报错 | 如实告知"提醒没设上"，但不要因此放弃整个导入 |

**永远不要**因为工具报错就假装已经写入了。
